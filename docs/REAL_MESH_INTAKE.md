# CBDK 実ユーザーメッシュ受け入れ手順（非公開・受入準備 v1）

> **状態:** 受入手順とローカル一覧化ツールを用意。実ユーザーモデルの読込・トポロジー診断・Blender実機検証は**まだ未実施**。公開リポジトリへ元データを追加しない。
>
> **既存開発との境界:** 既存のGLB-001〜022、ABCDのR14、STATE/Handoff、正式v0.17.0には干渉しない。モデル受入の記録は先にローカル非公開領域に保存する。

## 0. 提供・利用権限の確認

- 仕事先や顧客が権利を持つ3Dモデルは、**ChatGPTへ添付して共有すること自体**についても許可を確認する。本人制作でも、業務契約・守秘義務・商標・内部設計情報・顧客名などに注意。
- 共有許可がないモデルはアップロードしない。利用できない場合は本人がローカルで検査し、完全に独立した合成ダミーで不具合を再現する。マスキングした派生形状も自動的に公開可能とはならない。
- ファイルを提供されたことは、GitHub・CI・Notionでの公開、再配布、製品への同梱、第三者への共有の許可とは**別**。
- 元モデル、テクスチャ、内部寸法、座標、ファイル名、派生GLB、比較HTML、解析画像、スクリーンショット、ハッシュ、ログは原則非公開。匿名化だけで秘匿性は保証できない。

## 1. 保管場所と準備コマンド

CBDKリポジトリ直下に次の構成を用意（初回はツールがフォルダを作成）。

```text
test_meshes_private/             # Git ignored — original work/reference meshes
  reference/                    # comparison baseline (例)
  candidate/                    # processed / modified result (例)
  edge_cases/                   # holes, thin walls, dense topology, etc. (例)
reports/private_mesh_intake/    # Git ignored — source-derived manifest/evidence
  manifest.json
```

```powershell
# CBDKのルートから。最初は test_meshes_private/ だけを生成してもよい
python scripts/mesh_intake.py

# 権利確認済のモデルを test_meshes_private/reference/ へ手動コピー後
python scripts/mesh_intake.py --role reference
```

このコマンドは **読取専用のファイル棚卸し**。形式、ローカル相対パス、サイズ、SHA-256、匿名モデルID、仮の用途、未検証状態をローカルJSONへ記録する。ファイル内容の解析、Blenderでの開封、外部URL取得、ZIP解凍、任意スクリプトの実行、ネットワーク送信はしない。出力には私有ファイル名が含まれるため、`manifest.json` を公開しない。

対応する棚卸し拡張子: `.blend`, `.glb`, `.gltf`, `.stl`, `.obj`, `.fbx`, `.ply`, `.3mf`。**拡張子の認識は「読み込める・安全・正しい形状」の証明ではない**。`zip`や外部参照ファイルは自動展開しない。1ファイル最大4GiB。空ファイル、シンボリックリンク、非対応形式、読取失敗ファイルはスキップ。

`--role` は一度の走査で見つけた全ファイルに付く仮ラベル。`unassigned` が既定。参考用と編集後を分けたい場合はフォルダを整理し、用途ごとの本登録は**個別にレビューしてから**実施する（v1はモデル間の自動ペアリングをしない）。

## 2. 受入時のテスト用途

| 種別 | モデルで確かめる項目 | 既存機能への対応 |
|---|---|---|
| 基本形状 | 頂点/面数、原点、寸法、座標系、オブジェクト構造 | GLB-001/003、Mesh Inspector |
| 形状回帰 | 変更前後、シルエットIoU、表面差、部品対応の曖昧さ | GLB-003/004/019/020 |
| メッシュ品質 | 開いた辺、非多様体、極薄肉、内壁、重複面、分離パーツ | GLB-020の既存検査と今後の回帰 |
| 加工・操作 | 選択、頂点移動、監査、復元、モディファイアの影響 | BME-001〜003、BLGEO-001/BLMOD-001 |
| 性能・耐性 | 大きい面数、細密曲面、多数部品、メモリと打切り | PERF-001、各GLB解析の安全上限 |

受入後の状態は `received` → `permission_checked` → `inventoried` → `format_reviewed` → `local_blender_tested` → `regression_candidate`。前段階の達成は次の段階の合格を意味しない。失敗・保留・未実行を明示する。

## 3. ファイルを受け取った後の標準作業

1. 共有権限・秘密情報・用途を確認し、原本を**変更しない**。必要なら解析用の別コピーを作る。
2. 対応形式・サイズ・外部参照・同梱スクリプトを確認。未検証ファイルは信頼済みアドオンとして扱わない。
3. 非実行の一覧化ツールでローカルIDを採番し、モデルの特徴と狙い（例: 「穴が開いている」「高密度曲面」）を内部で分類。
4. 実際の形状解析は明示的に選んだ既存の安全検査フローへ。最初は静的形式検査と合成データで、Blender必要時は隔離環境・factory startup・自動スクリプト実行無効・上限付きで実施。`.blend`の自動オープン、埋め込みPythonやドライバなどの自動実行は禁止。
5. 既存のテストを回す場合、テスト対象の版、所要時間、測定上限、成功/失敗/未判定、元ハッシュ不変を内部記録。モデルから抽出した見た目や座標をGitHub ActionsのArtifactsへ転送しない。
6. 公開CIが必要な欠陥には、**仕事用形状を再構成しない独立の合成モデル**を新規作成して確認。公開範囲について権利者から許可がない限り私有派生成物は公開しない。

## 4. 送ってもらえると助かる最小情報（任意）

モデルファイルに加え「**参照用 / 修正前 / 修正後 / 不具合例**」のどれかと、目的（たとえば「接合部が細い」「曲面が多い」）だけでよい。サイズ単位・Blender版・予想される結果が分かれば後から追記可能。ユーザーに一括して長い入力表を要求しない。

## 5. 開発チームへの申し送り

- B: GLB診断と合成再現の確認に使う。実形状を公開CIへ組み込まない。
- C: UI表示、選択/編集モード、実際の作業手順の知見を得る。私有アセットを生成プレビューに同梱しない。
- D: 形式・権限/外部参照・異常入力拒否・各解析の上限を確認。私有モデルを第三者配布用fixtureにしない。
- A: 集約するのは**個人・会社・形状の特定に結び付かない開発課題**と、独立に作成した合成テストの結果だけ。STATE/Handoff/NotionはAの通常節目で更新し、今回の準備だけで実ユーザーモデル検証済にしない。

## 6. 今回の完了条件と限界

- `test_meshes_private/` と `reports/private_mesh_intake/` はGit管理外。
- 棚卸しCLIとPythonテストが追加され、公開コードには実モデルを含めない。
- **まだ行わない:** 元モデルの自動読込・修復・Blender実機評価、モデル間の自動紐付け、仕事用データのGitHub保存、正式部品採用。
