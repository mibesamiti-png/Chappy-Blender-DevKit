# CBDK 長期ビジョン — AI自律開発・3Dモデリング支援エンジン

**正式な長期設計方針：2026-11-11 JSTユーザー決定。製品機能としては未実装。** 設計採択と、実装・検証・リリースの承認を区別する。

[PROJECT_SPEC](../PROJECT_SPEC.md) と [STATE](../project/STATE.json) が現行正本。v0.19〜v0.22の承認済み計画は [人間向け](CBDK-FUTURE-019-022.md)・[機械可読](CBDK-FUTURE-019-022.json)を参照（現時点では `active=false`）。

## 1. 最終的な二つのエンジン

- **AI自律開発エンジン** — 人間の目的・制約・許可に従って調査→設計→実装→テスト→改善→記録→引き継ぎを支援する。CI成功・コード生成だけで採用/公開の許可を付与しない。
- **3Dモデリング支援エンジン** — 形状・トポロジー・制作目的を理解して生成→編集→接合→修復→比較→検証を支援する。合成fixtureの改善を任意の実作品の成功に一般化しない。

両系統は独立に開発・検証し、知識ID、技術ライブラリ、来歴、作業状態、評価証拠等のうち安全かつ有用な範囲だけ共有する。複雑性・依存・権限リスクが増す場合は無理に統合しない。

## 2. ユーザー決定の4大仕様

IDは [Development Intelligence Lab PR #115](https://github.com/mibesamiti-png/Chappy-Blender-DevKit/pull/115) のLT-01〜LT-12提案体系に対応させる。ユーザー説明上のLT-01〜04を別体系として重複採番しない。現在のSTATE requirements/NEXTへ未実装機能を追加しない。

| 基本仕様 | 対応ID | 将来の安全・受け入れ条件 |
|---|---|---|
| 自律／共同制作モード | **LT-01** | 目的・制約・予算・権限を保持し、途中切替で公開範囲や編集許可を自動的に拡大しない |
| 対象ごとの排他的操作権 | **LT-02、LT-03、LT-04** | 単一writer、旧世代書込み拒否、安全区間で人間へ引継ぎ、変更差分を確認してAIへ再開 |
| 安全な中断・保存・再開 | **LT-03、LT-04、LT-05** | 検証済みcheckpointと読戻し確認。強制停止・異常終了・破損・復元不能を成功表示しない |
| 任意時点の進捗確認 | **LT-06、LT-07** | 手動／低頻度更新。工程・検証済み成果・保存済みプレビュー・差分・エラー・次工程・観測時刻と鮮度を示す |

追加の候補：**LT-08** 高度AI非依存、**LT-09** 知識の来歴と再利用、**LT-10** 反証可能な品質・速度・費用の比較、**LT-11** プライバシー・公開境界、**LT-12** 段階導入と撤回。

### 将来の具体的な安全契約

- **モード:** 自律モードは許可された工程の委任、共同制作モードは人間が直接編集しAIが部分支援。モードの切替は権限付与と同義ではない。
- **操作権:** 同じ .blend、共有datablock、生成先、worktree等は名前が違っても競合し得る。旧writer遮断と対象revision/世代確認を将来検証する。現状それらのロック機構を実装済みと表現しない。制御できなければ別コピー方式を採る。
- **停止・復旧:** 安全な工程境界で中断し、成果と依存・履歴を保存し、再読込検証後のみcheckpointを確定。人間の変更・未保存データ・異常終了・強制停止を上書きしない。未検証の復旧は確認待ち／復旧不可／状態不明とする。
- **進捗:** 作業中／一時停止／確認待ち／失敗／完了を区別。状態にwork/attempt/revision、観測時刻、取得鮮度、検証種別を紐付ける。PR/CI成功と実executorの生存・制作目的達成は別。heartbeat欠落や古い記録は現在実行中と推測しない。根拠のない進捗率・ETAを非表示にする。
- リアルタイム映像配信は必須ではない。手動または低頻度更新と、保存済みrevisionに対応する途中成果で十分。

## 5. 高度AIへの依存軽減と導入原則

決定的な差分取得、静的検査、ハッシュ・CI照合、手順化された文書生成等は通常Python/Node/GitHub Actions/ローカルツールを優先する。通常ChatGPT・Codexは限定した調査・実装支援、高度AIは難しい仮説・設計判断へ選択的に使う。AIの種類や稼働状況は操作許可・品質の証明ではない。必要なAIが利用不能でも安全な独立作業は継続し、根拠の欠ける工程だけ確認待ちにする。

採用は **独立研究→既存方式との比較と故障・費用・品質評価→Aレビュー→必要なら別の正式機能PR→正確なHEADでの検証→明示的な統合判断** の順。私有GLB・アドオンの無断実行、外部送信、公開、mainマージ、正式リリース、現行品質ゲートの省略を認めない。

**本書で正式登録するのは最終目標と設計方針だけであり、自律制作・操作権・中断復旧・監視機能の実装ではない。**
